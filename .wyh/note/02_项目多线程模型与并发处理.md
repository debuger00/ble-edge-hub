# 02 项目多线程模型与并发处理

## 一、整体线程结构

本项目使用 C++ `std::thread` 实现多线程，没有使用 Python `asyncio`，也没有使用线程池。

```text
主线程
├── TCP accept 线程
│   ├── 网关 Session 线程 1
│   ├── 网关 Session 线程 2
│   └── 网关 Session 线程 N
├── WebSocket accept 线程
│   ├── WebSocket 客户端线程 1
│   └── WebSocket 客户端线程 N
└── SQLite 数据库写入线程
```

主要源码：

- `src/main.cpp`：主线程、CLI 和服务启停；
- `src/services/tcp_server.cpp`：TCP 监听线程和网关 Session 线程；
- `src/services/websocket_server.cpp`：WebSocket 监听线程和客户端线程；
- `src/services/database_writer.cpp`：SQLite 后台写入线程；
- `src/services/inference_engine.cpp`：推理窗口管理，本身不创建线程。

## 二、TCP 多线程模型

`TcpServer::start()` 创建 TCP accept 线程：

```cpp
accept_thread_ = std::thread(&TcpServer::accept_loop, this);
```

accept 线程只负责监听新的网关连接。每当一个网关连接进来，程序创建一个 `Session` 对象，并为该网关创建独立线程：

```cpp
worker_ = std::thread(&Session::run, this);
```

因此每个网关有自己的数据处理线程：

```text
网关 A → Session A 线程
网关 B → Session B 线程
网关 C → Session C 线程
```

Session 线程主要负责：

1. 使用 `poll()` 等待 TCP 数据；
2. 使用 `recv()` 接收数据；
3. 使用 `StreamDecoder` 解析 TCP 字节流；
4. 处理传感器数据和连接状态；
5. 发送网关控制命令；
6. 定时查询电池和发起自动重连。

核心循环可以理解为：

```text
等待网络事件
    ↓
接收 TCP 数据
    ↓
协议解码
    ↓
传感器解析
    ├── 加入数据库队列
    ├── WebSocket 广播
    └── 推理处理
```

## 三、WebSocket 多线程模型

WebSocket 服务有一个 accept 线程：

```cpp
accept_thread_ = std::thread(&WebSocketServer::accept_loop, this);
```

每接入一个浏览器客户端，就创建一个线程处理 HTTP Upgrade 握手：

```cpp
workers_.emplace_back(&WebSocketServer::handle_client, this, client);
```

握手完成后，客户端 socket 被加入 `clients_` 列表。之后 TCP Session 线程调用：

```cpp
websocket_.broadcast(...);
```

向所有客户端同步发送数据。

当前 WebSocket 主要用于服务端单向推送，尚未实现完整的客户端帧解析、Ping/Pong、分片和业务控制命令。

## 四、SQLite 异步写入

TCP 线程收到 `SensorSample` 后，不直接操作 SQLite，而是调用：

```cpp
database_.enqueue(*sample);
```

`DatabaseWriter` 内部有一个有界队列：

```cpp
std::deque<SensorSample> queue_;
```

数据库写入线程通过 `std::condition_variable` 等待队列中的数据：

```cpp
ready_.wait_for(lock, std::chrono::seconds(2), ...);
```

它每次最多取 100 条样本，然后使用 SQLite 事务批量写入：

```text
BEGIN
插入多条样本
COMMIT
```

这样可以避免磁盘 I/O 阻塞 TCP 接收线程。

队列默认容量是 10000。当队列满时，新的样本会被丢弃并打印警告：

```cpp
if (queue_.size() >= queue_capacity_) return false;
```

这是项目中的一种背压策略：限制内存占用，但牺牲部分数据。

## 五、推理线程模型

`InferenceEngine` 本身没有独立线程。它在 TCP Session 线程中被同步调用：

```cpp
inference_.process(*sample);
```

每个传感器 MAC 地址拥有独立的滑动窗口：

```cpp
std::unordered_map<std::string, DeviceWindow> windows_;
```

配置示例：

```yaml
window_size: 50
stride: 5
```

含义是：

- 收集 50 个加速度样本后形成一个窗口；
- 之后每新增 5 个样本执行一次推理；
- 模型输入按照 `X全部样本 + Y全部样本 + Z全部样本` 的 Channel-Major 格式排列。

TensorRT 内部使用 CUDA stream，但最终调用 `cudaStreamSynchronize()` 等待结果，所以从 TCP Session 线程角度看，当前推理仍然是同步操作。

## 六、线程同步机制

### 1. `std::atomic`

用于控制线程生命周期：

```cpp
std::atomic<bool> running_{false};
std::atomic<bool> active_{false};
```

多个线程可以安全地读取和修改这些状态。

### 2. `std::mutex`

用于保护共享数据：

```text
sessions_mutex_ → TCP Session 列表
state_mutex_    → 网关发现和连接状态
queue_mutex_    → 网关待发送命令队列
clients_mutex_  → WebSocket 客户端列表
Inference mutex → 各设备的推理窗口
```

### 3. `std::condition_variable`

用于数据库生产者和消费者之间的通知：

```text
TCP 线程 enqueue()
       ↓ notify_one()
SQLite worker 被唤醒
```

### 4. `join()`

服务停止时，主线程会等待各个工作线程结束：

```cpp
worker_.join();
```

这样可以避免对象已经析构，但工作线程还在访问对象成员。

## 七、服务停止顺序

主线程收到 `SIGINT` 或 `SIGTERM` 后，按以下顺序停止服务：

```cpp
tcp.stop();
websocket.stop();
database.stop();
```

停止时通常会：

1. 修改运行状态变量；
2. `shutdown()` socket，使阻塞的网络调用返回；
3. `close()` socket；
4. `join()` 等待线程结束；
5. 最后释放服务对象。

## 八、当前并发模型的优点

- 不同网关之间相互隔离；
- 数据库写入不会直接阻塞网络接收；
- TCP 半包和粘包由独立解码器处理；
- 数据库队列有容量上限，避免内存无限增长；
- 数据库使用批量事务，提高高频写入效率；
- 共享状态使用 mutex 保护。

## 九、当前并发模型的限制

1. 一个网关一个线程，连接数很多时线程数量会快速增长；
2. WebSocket 广播是同步的，慢客户端可能阻塞其他客户端；
3. 推理在 TCP Session 线程中执行，耗时推理会影响网络处理；
4. `InferenceEngine` 使用全局 mutex，多个设备的推理可能串行化；
5. TCP 出站命令队列目前没有容量限制；
6. 断开的 Session 不能及时从 Session 列表移除；
7. WebSocket 工作线程在服务停止时才统一回收。

## 十、总结

这个项目的并发模型可以概括为：

```text
多线程
+ 阻塞式 POSIX Socket
+ poll()
+ mutex
+ condition_variable
+ 有界数据库消息队列
```

它不是 `asyncio` 或完整的异步事件循环。

最关键的数据流是：

```text
TCP 字节流
    ↓
StreamDecoder
    ↓
SensorSample
    ├── DatabaseWriter 队列
    ├── WebSocket 广播
    └── InferenceEngine 滑动窗口
```

如果未来要支持更多网关和浏览器连接，可以考虑使用 `epoll`/`io_uring`、事件循环、独立推理任务队列以及每个 WebSocket 客户端独立的发送队列。
