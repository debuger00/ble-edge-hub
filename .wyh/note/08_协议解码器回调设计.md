# 08 协议解码器回调设计

记录日期：2026-09-08

## 1. 一句话概括

`StreamDecoder` 是一个**无状态、推式（push）的解码器**：你只把原始字节喂进去，它内部拼出完整帧后，**不返回、不存储**，而是通过构造时注入的回调把结果「吐」出来。解码器只负责「字节流 → 完整帧」，帧之后干什么它一概不管。

## 2. 核心思想：推式 + 回调注入

常见的「拉式（pull）」设计是：调用方反复问解码器「有完整帧了吗？给我」。而这个项目用的是「推式」：

```text
recv 原始字节 → append() → 内部 buffer_ → consume_one() 拼帧 → callbacks_.on_xxx() 回调出去
```

解码器不返回解析结果，而是提前拿到一组回调函数，解出什么就调什么。这是典型的**回调 / 观察者 / 依赖注入**模式。

## 3. append 与内部缓冲

文件：[gateway_codec.cpp](../../src/protocol/gateway_codec.cpp)

```cpp
void StreamDecoder::append(const std::uint8_t* data, std::size_t size) {
  buffer_.insert(buffer_.end(), data, data + size);  // ① 追加进内部缓冲区
  while (consume_one()) {}                            // ② 循环尝试解出完整帧
  if (buffer_.size() > max_frame_size_) { ... }      // ③ 缓冲超限就清空重同步
}
```

- `buffer_` 只存**尚未解完的原始字节**，不是存结果。
- `consume_one()` 每成功解出一帧就返回 `true`，`while` 循环把缓冲里能解的全解完——因为一次 `recv` 可能收到多个帧，也可能只收到半帧。
- 超限保护：缓冲超过 `max_frame_size_` 说明失去同步，直接清空重来，防止内存无限增长。

## 4. 帧同步与校验

`consume_one()` 先看前两个字节判断帧头（`gateway_codec.cpp:73-80`）：

```cpp
constexpr std::uint8_t kGatewayHead0 = 0xac, kGatewayHead1 = 0xca;  // 网关数据帧头
constexpr std::uint8_t kScanHead0 = 0xad, kScanHead1 = 0xba;        // 扫描帧头
```

对不上帧头就把最前面一个字节丢掉、继续找（`buffer_.erase(buffer_.begin())`），这是一种**字节级重同步**——容忍半帧、粘包、脏字节。

网关数据帧的解析（`consume_gateway_frame`）大致结构：

```text
[0..1]  帧头 0xac 0xca
[2..3]  帧总长度（大端 16 位）
[4..9]  网关 mac（6 字节）
[10..11] message_id（大端 16 位）
[12]    type 帧类型
[13..len-2] payload
[len-1] xor 校验和
```

解析时先校验长度合法、缓冲区够不够一整帧、`xor_checksum` 是否匹配，全部通过才组装 `GatewayFrame`。

## 5. DecoderCallbacks：四个钩子

文件：[gateway_codec.hpp](../../include/iot/protocol/gateway_codec.hpp)

```cpp
struct DecoderCallbacks {
  std::function<void(const GatewayFrame&)> on_gateway_frame;  // 解出完整网关帧
  std::function<void(const ScanEvent&)> on_scan;              // 扫描到设备
  std::function<bool(const std::string&)> allow_scan_device;  // 是否允许这个设备
  std::function<void(const std::string&)> on_error;           // 解码出错
};
```

解出结果时调用对应回调：

```cpp
if (callbacks_.on_gateway_frame) callbacks_.on_gateway_frame(frame);   // 网关帧
if ((!allow_scan_device || allow_scan_device(mac)) && on_scan) on_scan(event);  // 扫描（先白名单过滤）
if (callbacks_.on_error) callbacks_.on_error(message);                 // 出错
```

每次调用前都判空（`if (callbacks_.xxx)`），保证某个回调没注入时也不崩。

## 6. Session 如何接线

文件：[tcp_server.cpp](../../src/services/tcp_server.cpp)

解码器在 `Session` 构造时创建，并注入四个 lambda（`tcp_server.cpp:112-115`）：

```cpp
decoder_({[this](const GatewayFrame& frame) { on_frame(frame); },
          [this](const ScanEvent& event) { on_scan(event); },
          [this](const std::string& mac) { return config_.is_allowed_device(mac); },
          [this](const std::string& error) { log(LogLevel::warning, remote_ + ": " + error); }})
```

四个 lambda 都 `[this]` 捕获 `Session`，把解码结果转交给 `Session` 的成员函数或成员变量：

| 回调 | 转交 | 结果去向 |
|------|------|---------|
| `on_gateway_frame` | `Session::on_frame` | `handle_device_data` → `pipeline_.publish(sample)`；`handle_connection` → `connected_` |
| `on_scan` | `Session::on_scan` | `discovered_[event.mac] = DiscoveredDevice{...}` |
| `allow_scan_device` | `config_.is_allowed_device` | 白名单过滤的布尔判断 |
| `on_error` | `log(...)` | 打 warning 日志 |

## 7. 数据流向

```text
Session::run()
    → recv() 读字节
    → decoder_.append(bytes)      进 buffer_
    → consume_one()               拼出完整帧
    → callbacks_.on_xxx(frame)    回调出去
    → Session::on_frame / on_scan
    → discovered_ / connected_ / pipeline_.publish(...)
```

## 8. 为什么这个设计好

1. **职责单一**：解码器只管「字节 → 帧」，业务逻辑（怎么处理帧）留在 `Session`。两边的变化互不影响。
2. **解耦**：解码器不知道、也不关心帧被拿去干嘛——写库、推理、广播，都行。换个使用方只需换注入的回调。
3. **可测试**：想测解码器，注入假回调就能断言「解出了什么」；想测 `Session` 的业务逻辑，伪造一个假解码器即可。
4. **无状态、可复用**：解码器不保存解析结果，只留一个原始字节缓冲，逻辑干净，多个连接各持一个实例互不干扰。
5. **健壮**：字节级重同步 + 长度/校验和双重校验 + 缓冲超限保护，能容忍粘包、半帧、脏数据。

## 10. 网关接收数据的完整链路

`tcp_server.cpp` 中，接收数据不是在 `main.cpp` 里直接处理，而是在每个 TCP 网关连接对应的 `Session` 工作线程中完成：

```text
accept()
  ↓
创建 Session
  ↓
Session::start() 启动工作线程
  ↓
Session::run()
  ↓
poll() 等待 socket 可读
  ↓
recv() 接收 TCP 字节流
  ↓
decoder_.append()
  ↓
StreamDecoder 解析完整协议帧
  ↓
on_frame() / on_scan()
  ↓
具体业务处理
```

关键代码位置：

- `tcp_server.cpp:368-380`：`accept_loop()` 接受网关连接，创建并启动 `Session`；
- `tcp_server.cpp:176-186`：`Session::run()` 调用 `poll()` 和 `recv()` 接收数据；
- `gateway_codec.cpp:61-75`：`append()` 将字节放入内部缓冲区，并循环尝试解析；
- `gateway_codec.cpp:81-104`：`consume_gateway_frame()` 检查帧头、长度、校验和并组装 `GatewayFrame`；
- `gateway_codec.cpp:101`：解析成功后调用 `on_gateway_frame` 回调；
- `tcp_server.cpp:226-236`：`on_frame()` 根据 `frame.type` 分发业务；
- `tcp_server.cpp:238-274`：`handle_device_data()` 校验并解析传感器数据，最后投递到 `pipeline_.publish()`。

帧类型与处理函数的关系：

```text
0x20 → 传感器数据 → handle_device_data()
0x21 → 设备连接状态 → handle_connection()
0x22 → 心跳
0xF0 → 网关命令执行结果/错误
```

由于 TCP 是字节流，一次 `recv()` 可能只收到半帧，也可能收到多帧。`StreamDecoder` 的 `buffer_` 用来暂存尚未组成完整帧的原始字节，不能假设一次 `recv()` 就对应一条协议帧。

## 11. `on` 回调是什么意思？

`on` 不是 C++ 关键字，而是一种事件处理函数的命名习惯，表示“当某件事发生时执行”：

```text
on_gateway_frame
＝ 当网关帧解析完成时执行
on_scan
          ＝ 当扫描到设备时执行
on_error
         ＝ 当解码出错时执行
```

例如：

```cpp
decoder_({
  [this](const protocol::GatewayFrame& frame) {
    on_frame(frame);
  },
  ...
});
```

它表达的是：接码器解析出完整网关帧后，调用回调，把结果通知给 `Session` 的业务处理函数。

因此职责分工是：

```text
StreamDecoder：原始字节 → 完整协议帧
on_gateway_frame：通知外部“已经解析出一帧”
Session::on_frame：完整协议帧 → 具体业务处理
```

这里的回调是**同步调用**，不是另起线程的异步通知。`decoder_.append()` 在 `Session::run()` 中执行；解析成功后，会立即调用 `on_gateway_frame`，随后继续执行 `on_frame()` 和对应的业务处理。

之所以不把 `handle_device_data()`、`handle_connection()` 等业务代码直接写进 `StreamDecoder`，是为了保持职责单一和解耦。接码器不需要知道 `TcpServer`、设备白名单或数据管道，只负责解析；将来即使从串口、文件或其他网络连接读取数据，也可以复用同一个解码器。
