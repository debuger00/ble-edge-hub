# 09 网关与传感器通信寻址

记录日期：2026-09-14

## 1. 一句话概括

整个系统分**两段链路、两种寻址**：服务端到网关走 **TCP/IP（IP + 端口）**，网关到传感器走 **BLE（MAC + GATT handle）**。命令帧里因此有两个 MAC：帧头的 `gateway_mac`（网关）和 payload 里的 `target_mac`（蓝牙传感器）。

## 2. 两段链路、两种寻址

```text
服务端 ──TCP/IP（IP + 端口）──> 网关 ──BLE（MAC + GATT handle）──> 传感器
        ↑ 需要 IP                        ↑ 不需要 IP，只要 MAC
```

- **服务端 ↔ 网关**：走 TCP，需要 IP + 端口（config.yaml 里的 `tcp.port: 7628`）。
- **网关 ↔ 传感器**：走 BLE，链路层用 6 字节的 BLE 设备地址（配置里的 MAC）寻址设备，**不涉及 IP**。

一句话：**传感器侧不需要 IP，靠 MAC + GATT handle 就够了；IP 只用在服务端到网关这一段 TCP 上。**

## 3. 一条命令帧里的两个 MAC

| 位置 | 字段 | 含义 |
|------|------|------|
| 帧头 offset 4 | `gateway_mac`（`create_xxx_command` 第一个参数） | **网关**的 MAC，帧头字段，默认 `FF:FF:FF:FF:FF:FF`；是否表示广播/通配需查协议文档 |
| payload 开头 | `target_mac`（即 tcp_server 里传进来的 `mac` 变量） | **蓝牙传感器**的 MAC，payload 字段 |

所以 `connect_device` / `disconnect_device` / `configure_ready_device` 里的「设备」，指的是**蓝牙传感器**（imu948 / md9930），不是网关。

### 代码证据

```cpp
// tcp_server.cpp:133-138  连接设备
bool connect_device(const std::string& mac) {
  const auto normalized = normalize_mac(mac);                 // ← 传感器 mac
  const auto& profile = config_.profile_for_mac(normalized);  // 按传感器查 profile
  queue(protocol::create_connect_command(config_.gateway_mac, next_message_id(), normalized, ...));
  //                                        ↑帧头:网关               ↑payload:传感器
}
```

```cpp
// gateway_codec.cpp:162-172  连接命令的组装
Bytes create_connect_command(const std::string& gateway_mac, ..., const std::string& target_mac, ...) {
  Bytes payload{1};
  const auto mac = parse_mac(target_mac);              // ← 传感器 mac 进 payload
  payload.insert(payload.end(), mac.begin(), mac.end());
  ...
  return create_command(gateway_mac, 0x10, message_id, payload);  // ← 网关 mac 进帧头
}
```

`create_send_data_command`（写数据）、`create_disconnect_command`（断开）同理：`target_mac` 进 payload，`gateway_mac` 进帧头。

## 4. 帧结构里的 gateway_mac 位置

文件：[gateway_codec.cpp](../../src/protocol/gateway_codec.cpp)

```text
[0..1]   帧头 0xac 0xca
[2..3]   帧总长度（大端 16 位）
[4..9]   gateway_mac（6 字节）  ← 网关地址
[10..11] message_id（大端 16 位）
[12]     type 帧类型
[13..len-2] payload（含 target_mac + GATT handle + 数据）
[len-1]  xor 校验和
```

接收方向对称：`consume_gateway_frame()`（gateway_codec.cpp:97）也从 offset 4 读回 `frame.gateway_mac = format_mac(buffer_.data() + 4)`。当前服务端只是解析并保存这个字段，没有进一步用它校验网关身份。

## 5. GATT handle：传感器侧的属性寻址

传感器操作除了 MAC，还用 GATT attribute handle，进一步说明传感器侧是纯 BLE 通信：

```yaml
# config.yaml:29-39
sensor_types:
  imu948:
    notify_handle: 0x0008     # GATT 通知
    cccd_handle:  0x0009      # CCCD 描述符（使能 notify）
    write_handle: 0x0006      # 写入特征值
  md9930:
    notify_handle: 0x000A
    cccd_handle:  0x000C
    write_handle: 0x0014
    command_handle: 0x0012
```

下发给网关的命令，本质是「网关请用 BLE 对这个 MAC 的传感器，做某个 GATT 操作」：

```cpp
// gateway_codec.cpp:183-194  写数据命令
Bytes create_send_data_command(gateway_mac, message_id, target_mac, write_handle, data);
//                                       ↑帧头:网关      ↑payload:传感器MAC + GATT handle
```

## 6. 一个注意点：BLE 地址的稳定性

严格说 BLE 用的是 48 位的「BLE 设备地址」，分 **public** 和 **random** 两类；配置里的 `CE:43:75:25:96:BF` 属于 public 地址形式。这个地址是**出厂固定**还是**可随机化**取决于传感器固件——如果设备开了隐私随机地址，写死 MAC 就可能连不上。

所以「只要 MAC」这个结论成立的前提是：**传感器地址稳定不变**。

## 8. TCP 已经有 IP，为什么协议帧还要带 gateway_mac？

这个问题的关键是区分两个层次：

```text
服务器
  │ TCP/IP 连接（IP + 端口）
  ▼
蓝牙网关
  │ 解析 TCP payload 中的自定义命令帧
  ▼
BLE 传感器
```

命令帧确实是蓝牙网关自己的应用层协议，封装在 TCP 数据包的 payload 中。TCP 使用 IP 和端口找到网关；`gateway_mac` 则是协议数据中的设备身份字段，两者不属于同一个层次。

因此，`gateway_mac` 通常不是为了再次完成 TCP 路由，也不一定是真正的安全验证，而可能是协议设计中的固定字段，用于：

- 协议层确认“这条命令属于哪个网关”；
- 让网关固件进行地址检查；
- 支持多网关、转发或虚拟网关场景；
- 在响应帧中标识消息来源；
- 兼容历史协议格式。

如果系统始终是“一个服务器 TCP 连接对应一个蓝牙网关”，那么从网络通信角度看，帧中的网关 MAC 确实是冗余信息。但不能直接删除，因为它是自定义帧格式的一部分；删除后会改变字段偏移、帧长度和 XOR 校验和。

## 9. 当前项目是否真的验证了这个 MAC？

没有。当前代码的行为是：

1. 启动时从 `config/config.yaml` 读取 `gateway_mac`；
2. 发送命令时将它解析成 6 个字节并写入帧头 offset 4；
3. 接收帧时从 offset 4 解析出 `frame.gateway_mac`；
4. 没有把收到的 MAC 与配置值比较，也没有用它阻止或允许连接。

所以，当前 `gateway_mac` 的主要作用是**满足网关自定义协议的帧格式**，而不是服务器层面的网关认证。

`FF:FF:FF:FF:FF:FF` 是否表示通配、广播或“未指定网关”，不能仅凭本项目代码确定，必须以蓝牙网关厂商的协议文档或实际抓包结果为准。如果网关协议要求真实地址，应替换为实际网关 MAC。

此外，MAC 地址本身不是可靠的安全认证手段，容易被伪造；如果需要认证网关，应使用 TLS、密钥或登录认证机制。
